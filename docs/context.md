## Decisions made (do not re-derive, these came from explicit user answers)

### Auth
- **Phone number + PIN only.** No SMS/OTP, no third-party SMS vendor. PIN is the permanent login credential (replaces password in practice).
- Keep the `email` column/field on the backend user model for future-proofing, but it is not required and not used for login.
- Both signup paths must produce matching account structures: **customer self-signup** happens in the Next.js client (Go_Travel_Brightwings); **admin-created customers** happen in BrightP admin. Both must trigger the same auto-creation side effects (membership account, reward wallet, referral account, loyalty card, welcome bonus).

### Referral system (overrides the docx's simplified 3-level example)
- Referral relationships form an **arbitrary-depth tree** (referrer_id → referred_id adjacency), not a fixed 3-level structure.
- **Monthly batch job**, calculated at end of each month. This is the ONLY referral payout mechanism — no instant per-booking referral crediting.
- Flat **1% rate at every level** (not decreasing per level). Must be an **env variable** for easy tuning, not hardcoded.
- Calculation is on **that month's points only** (delta), not all-time cumulative.
- **Cascading rule**: process bottom-up. Each user's "monthly total" = their own points earned that month (bookings etc.) + referral bonus they received that month from their own direct referrals (computed earlier in the same pass). Their referrer then gets 1% of that monthly total, which flows further up.
  - Worked example from user: I have 5 direct referrals; their combined purchases earn 50,000 points this month → I get 500 (1%) referral points. The person who referred me then gets 1% of MY total for the month, which includes that 500 I just earned plus my own purchase-earned points. This repeats recursively up the chain to the root, however deep it goes.
- **Unlimited depth, but must be processed in a server-safe way** (no naive unbounded recursive query that can blow up/crash on a deep or wide tree) — implement as a bounded, iterative/batched bottom-up pass (e.g. process by tree depth level, or chunked iteration), not an unconstrained recursive CTE walking the whole tree in one shot.

### Done: referral system (migration 0009, new `referral` crate)
- `users.referral_code` (unique, 8-char random alphanumeric, generated at registration alongside `membership_code`, same collision-retry loop). `referrals` table: `referrer_id`/`referred_id` (referred_id UNIQUE -- each customer has exactly one referrer, fixed at signup, never mutated -- so the graph is a forest with no possible cycles, no cycle-detection code needed). `referral_payout_runs` tracks which `(period_start, period_end)` months have been paid, UNIQUE constraint guards double-runs.
- New sibling crate `src/modules/referral`, depends on `rewards` (one-way edge, no cycle). `auth` also depends on `referral` now (to call `record_referral` during registration) and on `rewards` (already did, for welcome bonus) -- dependency graph: `auth -> {rewards, referral}`, `bookings -> rewards`, `referral -> rewards`, `rewards -> nothing`. No cycles.
- Registration: `RegisterRequestDTO`/`AdminCreateUserDTO` both gained `referred_by_code: Option<String>`. `UserServiceImpl::register()` resolves the code to a referrer user_id BEFORE creating the user (fails with 400 `InvalidReferralCode` if unknown), creates the user, then calls `referral_service.record_referral()`. Shared by both self-signup and admin-create paths again (single `register()` method) -- satisfies the "must match" requirement.
- **Algorithm** (`ReferralServiceImpl::run_monthly_payout`, in `infrastructure/services/referral.rs`): loads all `referrals` edges + each user's point total earned in `[period_start, period_end)` (via new `RewardsService::monthly_earned_totals`), then does ONE in-memory bottom-up topological "peeling" pass (a node becomes ready once all its children are processed) -- no recursive SQL, no per-node DB round-trip, no recursion in Rust (iterative queue). At each node: `total = own_earned + referral_bonus_already_received_this_pass`; its referrer gets `round(total * rate / 100)` (rate = `REFERRAL_RATE_PERCENT` env var, default 1.0), and that amount is added to the referrer's own accumulator before the referrer itself gets processed -- this is what makes the cascade correctly compound up an arbitrary-depth chain in one pass. One combined `reward_transactions` row per referrer per run (not one per downline contributor). Marked `// ponytail:` with the scaling ceiling noted (fine to tens of thousands of edges; chunk/stream if it gets much bigger).
- **Double-run guard, sequencing matters**: `reserve_payout_run()` (unique-constraint insert) happens BEFORE any reward is awarded, and `finalize_payout_run()` (fills in totals) happens after. Originally had this backwards (recorded the run only at the end) which would have let a duplicate call re-pay everyone before hitting the conflict -- caught and fixed before considering the task done.
- New routes: `GET /referrals/me` (own referral_code + direct referral count -- lives in `app/src/routers/referral.rs`, not inside the `referral` crate itself, since combining a User field with a ReferralService count without creating a cross-dependency cycle is exactly what the app composition layer is for), `POST /admin/referrals/run-monthly-payout` (admin-triggered; **no in-process scheduler was built** -- wire an external cron/systemd timer to hit this monthly; flagged rather than assumed).
- Did NOT implement: any cap on chain depth (explicitly confirmed unlimited), per-tier rate variation (explicitly confirmed flat rate), real-time per-booking referral crediting (explicitly confirmed monthly-batch-only).
- Verified live end-to-end with a 3-level A->B->C chain: correct cascading math confirmed by hand (B's payout to A included the bonus B itself received from C earlier in the same pass), and re-running the same period returned 409 with no double-payment.
